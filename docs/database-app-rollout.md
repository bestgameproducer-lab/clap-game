# 数据库与应用安全上线顺序

本页只适用于包含 `202608130001` 及其后续迁移的这次安全升级。所有数据库操作仍须只向前执行；不得改写已应用迁移，不得在生产库清空、重新 seed 或手工回退函数。

## 为什么必须先进入全站零写入维护

当前线上旧版应用签发的私有照片路径是：

- 宾客头像：`宾客 ID/avatar.jpg`
- 任务照片：`宾客 ID/任务 ID/evidence.jpg`

从 `202608130001`、`202608130018` 开始，数据库只确认包含当前 `rehearsal_run_id` 的新路径。`202608130029` 只是临时恢复旧 RPC **签名** 的执行权限，不会也不能把旧路径安全转换成新路径。因此，数据库先升级而旧应用仍可操作时，旧版上传可以拿到 Storage 上传地址，但确认必然失败。

不能让数据库同时继续接受旧稳定路径。旧签名上传地址可能在彩排清场后才完成；若继续接受 `avatar.jpg` / `evidence.jpg`，它就能覆盖新一轮婚礼的数据，破坏 `rehearsal_run_id` 隔离。

仅关闭“宾客注册”不是维护模式。已经登录的宾客仍可上传头像或任务照片、提交任务、配对和投票；主控、主持人和任务站也仍可切换流程、核验和加分。

上线前必须满足下面二选一：

1. 在 Vercel/反向代理层阻断所有写方法（至少 `/api/**` 的 `POST`、`PUT`、`PATCH`、`DELETE`），并实测宾客、主控、主持人、任务站的代表性写请求都返回维护响应、没有写入数据库；或
2. 如果无法证明方法级阻断完整，发布全站维护页并阻断全部生产访问。

不要只隐藏按钮。不要只关闭注册。已经签发的 Storage 上传地址不经过应用服务器；进入维护后还应确认没有进行中的上传，并等待既有上传地址失效，之后再执行任何彩排清场。若后台显示私密照片清理待完成，不能重新开放现场。

## 推荐上线顺序（单次维护窗口）

这是最不容易出现旧应用/新数据库混用的方式：

1. 记录准备上线的 Git 提交与 Vercel 构建，完成必要导出；确认注册、投票和公开大屏均关闭。
2. 开启上述全站零写入维护；用代表性写请求验证维护确实生效。
3. 先运行迁移 dry-run，确认文件严格按名称排序，且没有缺号导致的错误推断。
4. 在维护期间先按名称顺序只应用 `202608130001`–`202608130030`。这部分建立数据完整性、run-scoped RPC、新应用入口和临时旧签名权限；此时**不得**执行 `202608130031` 或任何更晚的迁移。
5. 部署与上述迁移同一提交的新应用，核对 Vercel release SHA，并在维护仍生效时完成新入口的只读 smoke test。旧应用在这一步之前不得重新接收流量。
6. 新应用已经部署且 smoke test 通过后，严格按文件名顺序执行第二批：
   - `202608130031`：**POSTDEPLOY contract**，撤销临时旧 RPC 权限；
   - `202608130032`：每队一名额外投票权的第二轮分配器；
   - `202608130033`：第一轮照片任务可吸收性防护；
   - dry-run 中任何更晚的已审核 forward-only 迁移，继续严格按文件名顺序执行。
7. 保持维护状态，完成只读烟雾检查，再使用隔离测试身份检查：头像授权与确认、任务照片授权与确认、第二轮切换、主控/主持人加分。不得用生产宾客做破坏性测试。
8. 核对数据库迁移记录包含计划内全部文件、`202608130031` 已生效、私密照片清理无待处理，再关闭维护。

如果发布工具必须把数据库与应用拆成两个批次，也只能在**同一个持续维护窗口**内执行：先应用 `001`–`030`，部署并验证新应用，然后应用 `031` 及其后所有迁移。`001` 应用后到 `031` 完成前绝不能恢复生产写流量。

## 禁止的上线方式

- 不得在旧应用仍可写时先应用 `001`–`030`。
- 不得认为 `029` 已经让旧版上传兼容；它只解决 RPC 权限，不解决路径协议。
- 不得在部署失败后重新开放旧应用；数据库迁移不可回退，旧上传协议已经不兼容。应保持维护并修复/重新部署新应用。
- 不得为了恢复旧应用而手工 `GRANT`、手工改回 confirm 函数或放宽路径校验。
- 不得在 `031` 之前执行彩排清场，也不得在私密 Storage 清理仍待完成时开放下一轮。

## 上线后验收证据

- 当前应用提交、Vercel 部署提交与运维记录一致。
- 数据库迁移按 `001` → `030` → `031` → `032` → `033` → 后续迁移的顺序完整存在。
- 新应用只调用带 `rehearsal_run_id` 的 guest/staff/operator RPC。
- 旧 canonical RPC 已由 `031` 从 `service_role` 撤销。
- 头像与任务照片的新对象路径都包含当前运行 ID，清场前签发的旧路径不能被确认。
- 主控与主持人遇到第二轮照片任务契约异常时看到明确中文提示，而不是通用服务器错误。
